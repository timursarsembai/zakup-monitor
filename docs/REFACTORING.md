# План рефакторинга (2026-11-08)

Цель — чтобы проект было легко поддерживать: маленькие файлы с одной задачей, без
повторов, понятный порядок изменений в базе, быстрые тесты. **Поведение сайта и
ботов не меняется**: ни новых функций, ни изменений для пользователей. Каждый шаг —
отдельный коммит и выкладка (без перерыва), только при зелёных тестах.

## Что сейчас мешает

| Где | Проблема |
|---|---|
| `web.py` — 2 430 строк, 91 адрес | Всё в одном файле: вход, поиск, кабинет, оплата, настройки (25 адресов), дашборд, служебное. Трудно найти нужное, любая правка задевает всё. |
| Длинные функции | `dashboard.market` (129 строк), `__main__.main` (124), `web._announcement_context` (118), `filters.where` (104), `web._settings_page` (77). |
| `research.py` — 900 строк | В одном файле: подсказки для ИИ, три провайдера, очередь, чистка результатов, Kaspi, выжимки. |
| Повторы | Настройки ИИ администратора читаются одинаковым запросом в 8 местах; условие «клиент» и «кому положены уведомления» — в нескольких модулях. |
| Транзакции на время ожидания сети | Выжимки и вопросы поставщику ждут ответ модели с открытой транзакцией (то, что раньше давало DeadlockDetected). |
| Шаблоны | `settings.html` (413 строк) и `_filters.html` (409) — разметка, стили и скрипты вперемешку; 4 скрипта прямо в `base.html`. |
| Схема базы | Один `schema.sql` (550 строк) применяется целиком; история изменений не видна, откатывать неудобно. |
| Тесты | `test_web.py` — 1 200 строк; полный прогон 3,5 мин, из них ~2 — пересборка образа. |
| Настройки окружения | Переменные окружения читаются в разных модулях. |

## Шаги (в таком порядке)

1. **Быстрые тесты и проверка стиля.** Тесты в контейнере с подключённым кодом,
   без пересборки образа (≈1 мин вместо 3,5); добавить `ruff` (ошибки и неиспользуемое)
   в `scripts/test.sh`. Разбить `test_web.py` по разделам сайта.
   *Зачем первым:* каждый следующий шаг проверяется тестами — быстрее итерации.

2. **Убрать повторы и открытые транзакции.**
   - `ai_settings(conn)` — одно место для провайдера и моделей администратора.
   - Общие условия SQL («клиент», «положены уведомления») — в одном модуле.
   - Выжимки и вопросы поставщику — без транзакции во время ожидания модели.
   - `config.py` — все переменные окружения в одном месте.

3. **Разделить `web.py` на пакет `zakup/web/`** (адрес запуска `zakup.web:app` тот же):
   - `core.py` — пул соединений, шаблоны, зависимости (гость/клиент/тариф/сотрудник/админ), проверка источника запроса;
   - `middleware.py` — язык, сессия, статистика посещений, заголовки безопасности;
   - `public.py` — главная, поиск лотов и объявлений, страницы закупок, анализ рынка, документы, robots/sitemap;
   - `auth.py` — вход, регистрация, восстановление, организация, выход;
   - `cabinet.py` — мои лоты, подписки, лента, выгрузка;
   - `ai.py` — ИИ-подбор, источники, выжимки, вопросы поставщику;
   - `billing.py` — цены, оплата, вебхук, баланс;
   - `settings.py` — настройки (по вкладкам), пользователи, вход «как пользователь»;
   - `staff.py` — дашборд, журнал.

4. **Разделить `research.py` на пакет `zakup/research/`:** `prompts.py`, `providers.py`
   (Claude Code / Anthropic / OpenAI), `queue.py` (очередь, исполнитель, возвраты),
   `results.py` (чистка, объединение, маржа), `summaries.py`, `kaspi_query.py`.

5. **Разбить длинные функции:** `_announcement_context` — сбор данных по частям
   (портал, карточки организаций, телефоны, техспецификации); `_settings_page` — по
   вкладкам; `dashboard.market` — по блокам; `filters.where` — по условиям;
   `__main__.main` — таблица команд.

6. **Шаблоны:** `settings.html` — по вкладкам в отдельные файлы; скрипты из `base.html`,
   `_filters.html`, `lot.html` — в `static/*.js` с версией в адресе (кэш браузера).

7. **Миграции вместо одного `schema.sql`:** нумерованные файлы `migrations/0001_*.sql`,
   в базе — список применённых; `deploy.sh` останавливает сборщики только если есть новые.
   Текущая схема становится `0001_initial.sql` — для существующей базы ничего не выполняется.

## Как проверяем

- После каждого шага: все тесты зелёные, выкладка без перерыва, сайт и боты отвечают.
- Ночной ревьюер следующей ночью смотрит логи после изменений.
- Ни одного изменения в поведении: если по пути найдётся ошибка — отдельным коммитом и с пометкой.

## Не входит

- Новые функции и изменения интерфейса.
- Аудит безопасности — следующий этап, после рефакторинга (на чистом коде его проще и точнее делать).
