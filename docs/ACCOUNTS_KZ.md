# Личные данные в Казахстане, остальное в Германии

Решение владельца (2026-11-13): тяжёлое (сайт, сборщики, аналитика, ИИ) — на сервере
в Германии под адресом tenderim.com; личные данные — только на сервере в Казахстане
(сервис учётных записей, id.tenderim.com). tenderim.kz — позже. Юриста нет.

## Что считается личными данными

Телефон (он же логин клиента), почта, хэш пароля, сессии входа, IP-адреса попыток входа
и визитов, одноразовые SMS-коды. Сейчас это `users` и связанные таблицы основной базы.

Telegram остаётся в Германии (решение владельца 2026-11-14, вариант А): оба бота, номера
чатов пользователей и групп, все рассылки. Номер чата — без телефона и имени. Сервис в
Казахстане в Telegram не пишет никому.

## Как устроено

- Форма входа рисуется на основном сайте, но отправляется на id.tenderim.com. Сервис
  проверяет пароль и ставит cookie `tid` на весь `.tenderim.com` — подписанный Ed25519
  жетон: номер пользователя, номер сессии, время выдачи (`zakup_id/token.py`).
- Основной сайт проверяет подпись открытым ключом сам — без запроса в Казахстан
  (связь Германия ↔ Казахстан ≈ 0,1 с, на каждой странице это было бы заметно).
- Жетон «свежий» сутки; старше — сайт обменивает его на новый (`POST /api/renew`).
  Так выход, смена пароля и блокировка доходят до сайта не позже чем через сутки.
  Если Казахстан недоступен, старый жетон принимается до 3 суток: сайт работает.
- События сервиса для сайта: «у пользователя N телефон …2233 сменён на …1122» и
  служебные владельцу (перерасход SMS). Сайт опрашивает `GET /api/events`, отправляет в
  Telegram и подтверждает `POST /api/events/ack`; неподтверждённые приходят снова.
- В основной базе у пользователя остаются номер и настройки (подписки, тариф, роль, язык).

## Этапы

1. Домен tenderim.com (куплен 2026-11-14, DNS в Cloudflare) → основной сайт; zakup.sarsembai.com — 301 на него.
2. Сервис учётных записей (`src/zakup_id`, `deploy/kz/docker-compose.yml`):
   вход, выход, продление жетона, «выйти везде», регистрация и восстановление пароля
   по SMS, смена пароля и телефона, события для сайта — **готово** (не выложено).
3. Основной сайт на жетонах: проверка `tid`, продление, формы входа на id.tenderim.com,
   опрос событий сервиса (**без него сервис не выкладывать**: о смене телефона никто не
   узнает). Затем перенос данных, после проверки — удаление личных
   данных из немецкой базы и её копий. Переключение — с отдельного согласия владельца.
   В тот же момент /register, /forgot и смена пароля основного сайта ведут на
   id.tenderim.com, а их код (web/accounts.py, settings) удаляется: SMS-коды учитываются
   в базе сервиса, две работающие регистрации тратили бы двойной дневной запас SMS.

## Запуск в Казахстане (когда дойдёт)

    python -m zakup_id.keys >> deploy/kz/.env      # ключи — в файл, не на экран
    echo PROXY_NETWORK=<сеть nginx-proxy-manager> >> deploy/kz/.env
    echo ID_PROXY_IP=<адрес nginx-proxy-manager в этой сети> >> deploy/kz/.env
    docker compose -f deploy/kz/docker-compose.yml --env-file deploy/kz/.env up -d --build

Перенос учётных записей — с прежними номерами, затем `accounts.sync_ids`
(иначе счётчик новых столкнётся с перенесёнными). Порядок переезда:

1. В Казахстане: `ID_ALLOW_IMPORT=1` в deploy/kz/.env, перезапуск id-app.
2. Здесь (ZAKUP_ID_* заданы): `zakup id-migrate` — логины, хэши паролей (тот же scrypt —
   пароли прежние), телефоны, отключение и удаление; на экран — только номера записей.
   Повторять можно. conflicts — разобраться руками, дальше не идти.
3. Проверить вход на id.tenderim.com своим логином и паролем.
4. `zakup id-scrub` — проверка: missing — записи нет в Казахстане, different — под тем же
   номером там чужая запись (номер и ни логин, ни хэш пароля не совпали). Обоих не трогаем.
   Затем `zakup id-scrub --yes`: логины → «id:N», пароли и телефоны стёрты, логины в
   журнале действий — «id:N»; когда переехали все — из журнала стираются оставшиеся
   телефоны и e-mail, удаляются неудачные входы и SMS-коды.
5. Убрать `ID_ALLOW_IMPORT` и перезапустить id-app. Старые копии немецкой базы
   (~/backups) с личными данными — удалить после проверки.

Организация клиента (форма, БИН/ИИН, название — у ИП это ИИН и имя) и IP-адреса журнала
действий — тоже в Казахстане (решение владельца 2026-11-14): таблицы orgs и action_ips,
сайт спрашивает их, когда нужно (zakup.client_orgs, idservice.orgs/ips), и держит ответ до
10 минут в памяти процесса. IP новой записи журнала уходит туда в фоне. id-migrate переносит
и их, id-scrub стирает здесь то, что там уже есть то же самое.
Не переносится: журналы доступа веб-сервера (NPM) в Германии — в них тоже есть IP. После стирания телефона оплата через Kaspi не подставляет номер
клиента сама (users.phone пуст) — номер вводится вручную.

Память: база до 192 МБ, приложение до 256 МБ. Копии базы — тоже в Казахстане.

Открыто: контакты продавцов в каталоге — публичное предложение, оставить в Германии
(предложение) или перенести.
